# Writing Standards

## Purpose

This document defines the official writing standards for all documentation within the Universal Service ERP Documentation Library.

The objective is to ensure every document is written in a consistent, professional, and implementation-ready manner.

These standards apply to every contributor, including human writers and AI agents.

---

# Goals

This document aims to:

- Standardize documentation writing.
- Improve readability.
- Eliminate ambiguity.
- Increase consistency.
- Produce implementation-ready specifications.

---

# Non-Goals

This document does not define:

- Coding standards
- Programming conventions
- API design
- Database modeling

Those subjects are covered in their respective Books.

---

# General Principles

Every document should be:

- Clear
- Concise
- Complete
- Consistent
- Explicit
- Maintainable

Documentation should prioritize clarity over writing style.

---

# Language

All documentation must be written in English.

Business terminology, technical terminology, and user interface terminology must remain consistent throughout the repository.

Avoid mixing multiple languages within the same document.

---

# Writing Style

Documentation should use a formal and professional tone.

Avoid:

- Casual language
- Personal opinions
- Humor
- Marketing language
- Promotional statements

Documentation should describe facts rather than opinions.

---

# Sentence Structure

Prefer short and direct sentences.

Example:

Good

> The system validates the invoice before saving.

Avoid

> The system will probably try to validate the invoice before it is eventually saved.

---

# Voice

Prefer active voice.

Example:

Good

> The system generates the invoice.

Avoid

> The invoice is generated by the system.

Active voice improves clarity.

---

# Terminology

Always use canonical terminology.

A concept should have only one official name.

Example:

Use

- Purchase Order

Never alternate with

- Purchase Document
- Buying Order
- Purchase Form

Terminology is defined in the project glossary.

---

# Consistency

Similar concepts should be documented using the same wording and structure.

If two documents describe similar processes, they should follow the same organization.

---

# Explicit Definitions

Avoid assumptions.

Instead of writing:

> The system checks the data.

Write:

> The system validates that:

- Customer exists.
- Product exists.
- Quantity is greater than zero.
- Stock is sufficient.

Explicit rules reduce ambiguity.

---

# One Topic Per Document

Each document should focus on a single subject.

Do not combine unrelated topics into one document.

Large subjects should be divided into multiple documents.

---

# Single Source of Truth

Information should only exist in one authoritative location.

Other documents should reference it instead of duplicating it.

---

# Examples

Examples should illustrate the rule rather than replace it.

Examples must remain simple and easy to understand.

---

# Lists

Use bullet lists when presenting:

- Rules
- Requirements
- Responsibilities
- Conditions

Use numbered lists only when order is important.

---

# Tables

Use tables for:

- Comparisons
- Definitions
- Permissions
- Configuration
- Status mappings

Avoid using tables for long explanations.

---

# Diagrams

Complex workflows should be illustrated with diagrams whenever appropriate.

Diagrams complement documentation.

They never replace written specifications.

---

# References

Whenever a document depends on another document, reference it instead of repeating the information.

Cross references improve maintainability.

---

# AI Readability

Documentation should be optimized for AI consumption.

Therefore:

- Use consistent terminology.
- Avoid ambiguous wording.
- Avoid hidden assumptions.
- Define responsibilities explicitly.
- Separate business rules from implementation details.

---

# Document Quality Checklist

Before publishing a document, verify that:

- The purpose is clearly defined.
- The scope is correct.
- The terminology is consistent.
- The document contains no ambiguity.
- The information is complete.
- References are valid.
- No duplicate information exists.

---

# Summary

High-quality documentation is one of the project's most valuable assets.

Following these writing standards ensures that every document remains clear, consistent, maintainable, and ready for implementation.
