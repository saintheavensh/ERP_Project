# Business Events

## Purpose

This document defines the Business Event Framework used throughout the Universal Service ERP.

Business Events provide a standardized mechanism for communicating significant business activities between modules, workflows, services, and system components.

---

# Overview

A Business Event represents something important that has occurred within the system.

Events are generated whenever a meaningful business action takes place.

Examples:

* Service Order Created
* Device Received
* Diagnosis Completed
* Spare Part Consumed
* Stock Received
* Invoice Generated
* Payment Received
* Warranty Claim Approved

Events allow modules to react to business activities without tightly coupling their internal processes.

---

# Objectives

The Business Event Framework is designed to:

* Improve module interoperability.
* Support process automation.
* Reduce system coupling.
* Improve scalability.
* Enable notifications.
* Improve auditability.

---

# Event Fundamentals

## Business Event

A business event represents a completed business action.

Example:

```text id="evt1"
Technician completes diagnosis
```

Generated Event:

```text id="evt2"
DiagnosisCompleted
```

---

## Event Producer

An Event Producer is the module or process that generates an event.

Examples:

* Service Module
* Inventory Module
* Purchasing Module
* Finance Module

---

## Event Consumer

An Event Consumer is the module or process that reacts to an event.

Examples:

```text id="evt3"
Service Module
        ↓
Inventory Module
```

```text id="evt4"
Sales Module
        ↓
Finance Module
```

---

# Event Structure

Every business event should contain:

| Field         | Description       |
| ------------- | ----------------- |
| Event ID      | Unique identifier |
| Event Name    | Event type        |
| Event Time    | Timestamp         |
| Entity Type   | Related entity    |
| Entity ID     | Related record    |
| Source Module | Event producer    |
| User ID       | Responsible actor |
| Payload       | Event data        |

# Event Lifecycle

Business events generally follow:

```text id="evt13"
Business Action
        ↓
Event Generated
        ↓
Event Recorded
        ↓
Consumers Process Event
        ↓
Workflow Continues
```

Events themselves do not contain business logic.

Events simply communicate that something occurred.

---

# Event Naming Standards

Events should use consistent naming.

Format:

```text id="evt14"
<Entity><Action>
```

Examples:

```text id="evt15"
ServiceOrderCreated
DiagnosisCompleted
StockReceived
PaymentReceived
WarrantyApproved
```

Avoid ambiguous names.

---

# Event Processing Rules

## Rule 1

Events should represent completed business actions.

---

## Rule 2

Events should be immutable.

---

## Rule 3

Events should not be modified after creation.

---

## Rule 4

Events should contain sufficient information for consumers.

---

## Rule 5

Event processing failures should not corrupt source transactions.

---

# Event Logging

All business events should be recorded.

Benefits:

* Auditing
* Monitoring
* Troubleshooting
* Reporting
* Analytics

Event logs should remain searchable.
